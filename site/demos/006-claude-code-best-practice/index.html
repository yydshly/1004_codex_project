03 / 工作原理

模型做判断，工具做操作，结果再反馈。

Agentic loop / 代理执行循环

Markdown 文件提供任务知识；Claude Code 把相关指令、源码和工具结果放进上下文，驱动一次次推理与执行。点击下面的步骤，查看各环节的职责。

◎
用户 / 任务定义

先说明要实现什么，以及如何确认成功。

例如：修复登录失败，保留现有接口，相关测试通过。清楚的目标和验收条件，能帮助后续每一步围绕同一个任务展开。

反馈 → 下一步
知识按需进入

Skills 提供上下文

先暴露名称和触发描述，使用时加载完整做法，参考资料按需读取。子代理的 skills 字段也可以预加载技能说明。

过程分开保存

Subagents 隔离上下文

研究和搜索日志留在子任务里，主会话接收结果。并行修改同一工作区时，仍需考虑文件冲突。

执行层承担约束

权限与 Hooks 控制操作

“必须先测试”是文字要求。程序权限、阻断脚本和实际测试结果，分别承担限制、检查与验证。

依据：官方执行循环 · 子代理 · 扩展机制与约束

05 / 场景与价值

选一个实际任务，再判断是否值得引入。

场景取舍 / 基于能力的研究判断
从问题开始

每天都在重复解释同一套检查步骤。

例如提交前检查、变更说明、固定格式的代码审查。把稳定的做法沉淀为一个 Skill 或 Command。

CommandsSkills参考模板
可获得的价值
减少重复提示，稳定任务输入、执行要求和输出格式。
如何确认有用
观察重复输入次数、漏检项和产出是否符合检查清单。
引入与维护成本
需要把有效步骤提炼清楚，并在工具或项目约定改变时更新。
临时经验→可复用指令→清晰的任务交接→可检查的工程结果

价值来自工作方式的改进。实际收益取决于任务、模型、工具与验证质量；本研究没有测量生产效率提升或错误率下降。

06 / 如何借鉴

从一个经常重复的任务开始。

01

补齐项目基础信息

记录构建、测试、目录约定和验收方式，让新会话能找到正确的工作入口。

02

选一个流程做成技能

从仓库挑选相关模板，换成自己项目的输入、操作步骤、工具和交付要求。

03

验证后，再增加分工

检查实际产出；任务足够复杂时再加入子代理、外部工具或阶段验收。

借鉴前，分清这些边界

按需要选择模板，
按实际结果判断效果。

  • 运行环境：示例需要 Claude Code、模型访问，以及对应网络、工具和文件权限。
  • 外部资源：README 收录的框架和 MCP 工具需分别安装配置；本库展示其用法与入口。
  • 权限与约束：文字中的“只读”“必须”属于任务要求，仍需核对真实工具权限和检查逻辑。
  • 示例范围：天气示例固定查询迪拜温度；仓库的 Hooks 脚本主要做通知和日志。
  • 维护成本：说明、模型配置和工具字段可能随版本变化，需要与实际文件、官方文档核对。

07 / 选用与实践

从你的目标，选择最小的组合。

选用建议与原创适配示例

先判断触发方式，再考虑上下文、工具和验收。下方取舍属于本页研究建议。

建议起点

Skill · 一个可重复调用的流程

把稳定步骤、参考资料与输出要求保存下来；用户通过 /名称 主动调用，也可按描述由模型选用。

需要承担的成本

提炼触发条件与验收标准，并随项目约定维护。

查看对应机制 ↑
不同机制的主要职责
选项触发与上下文最适合解决
直接提示一次请求，使用当前上下文单次解释、小范围修改、输入已齐全的任务
CLAUDE.md / rules会话启动或匹配相关路径时加载构建命令、目录约定、跨任务持续使用的知识
Skill / Command 入口显式调用或按描述发现；默认在当前会话使用重复步骤、领域说明、模板与脚本；也可配置 fork
Subagent被委派任务；使用独立上下文大量检索、专门审查、可明确交接的子任务
Hook匹配的生命周期事件触发事件记录、通知、格式化或经验证的阻断检查
MCP运行时连接服务，模型调用工具把外部系统的操作和数据接入任务

当前 Commands 与 Skills 已合并，旧命令目录继续兼容。新建示例采用 Skill 格式，三层编排适合需要分工的任务；简单任务可以直接完成。官方职责对照 ↗

把原则落到文件 / 原创教学示例

把“检查这次改动”变成一次可复用调用。

下载示例包 ↓
  1. 整理项目知识。把示例中的构建、测试与目录说明换成实际信息，合并进现有 CLAUDE.md。
  2. 保存审查技能。把示例 SKILL.md 放到 .claude/skills/review-change/，核对当前工具与权限设置。
  3. 主动调用与核对。在 Claude Code 中输入 /review-change，明确修改范围；再按检查清单核对产出。

这是本页编写的学习模板，借鉴仓库的组织方式；未在 Claude Code 中运行。示例文字不替代权限设置。

输入 / 输出 / 验收

一次任务应该留下什么？

明确输入
目标、修改范围、相关 diff、项目约定与可执行的检查方式。
可复查输出
行为变化、问题对应的位置与理由、已执行的检查、尚未验证的部分。
完成依据
需求是否满足，发现能否复现，相关检查是否通过，阻碍是否已说明。
失败反馈
记录缺依赖、工具错误、权限拒绝或验证失败；调整后再次核对。
价值验证 / 避免只看流程变复杂

用同一类任务，比较封装前后的变化。

复用收益

少解释了什么？

记录重复输入、临时补充与遗漏项，检查模板是否减少相同问题。

产出质量

结果是否可核对？

比较需求覆盖、具体证据、未验证项与实际返工，复查每条发现。

全部成本

付出了多少工作？

一起记录首次适配、维护、模型使用、工具执行和子任务协调成本。

比较时尽量保持任务类型、代码范围、模型和验收标准一致。本页提供观察维度，不提供未经测量的效率或准确率结论。

实际迁移时，核对三件事。

目录与知识加载

项目整体约定放根目录，组件规则按工作路径组织。Skills 的触发与预加载需要分别判断。

工具授权的含义

Skill 的 allowed-tools 是免确认授权。实际限制需核对权限规则、子代理工具配置与阻断逻辑。

事件脚本的行为

本库 Hooks 配置为异步声音与日志处理。异步执行不能作为阻止工具行为的检查点。

知识组织示例 · allowed-tools · 仓库事件配置 · 异步 Hook 边界

几个容易混淆的问题

读取这个仓库，就能自动掌握所有内容吗？

与当前工作路径相关的项目指令会由运行时加载。普通研究报告与外部链接，需要按任务读取；技能通常只在相关或调用时加载完整内容。

写好一段提示，与配置这些机制有什么区别？

提示提供目标与知识。运行框架还负责实际工具、上下文分工、权限和事件调度。单次小任务可以直接提示；重复或复杂任务再按需要组织这些能力。

可以把这些文件用到其他编程助手吗？

其中的任务知识与检查方法可以改写复用。目录、字段、触发方式、工具名称和权限语义属于具体工具，迁移时需要逐项核对。

“流程执行完成”就代表代码正确吗？

完成状态说明任务走到了交付环节。代码行为需要测试、运行观察、审查与验收证据支持，文件和结论应能回到实际输入。
