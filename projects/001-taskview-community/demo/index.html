TASKVIEW COMMUNITY / 源码研究

TaskView Community
任务管理平台与 Agent 接入

TaskView 提供带界面的任务管理平台，包含后端 API、权限、数据库与事件处理。它可独立用于人工协作，也可作为外部 Agent 的任务入口和进度面板。

研究摘要 / 先读这六点

这个库能做什么，能为我们带来什么？

Gimanh/taskview-community 是可自托管的项目与任务管理产品。前端提供工作视图，后端提供业务逻辑与数据管理。普通团队由成员完成工作；接入外部 Agent 后，平台可承载任务分配、上下文和进度回写。

能力
项目、任务与子任务、看板、依赖图、Sprint、重复任务、成员权限、历史、工时统计，以及开发工具和消息集成。
底层原理
Vue 界面通过 Express HTTP API 访问业务层；权限检查后，由 Drizzle 操作 PostgreSQL。任务变更产生事件，驱动通知、Webhook 和周期业务。
使用场景
内部研发和迭代管理、个人项目、内部客户交付记录，以及人和 Agent 共用的工作清单与状态面板。
入口
Web / 移动端人工操作、HTTP API、TypeScript 客户端、MCP 工具调用，以及 Git 仓库或消息平台事件。
出口
任务数据与状态、可视化视图、历史和工时报表、通知、签名 Webhook，以及已关联 Issue 的完成状态回写。执行产物由成员或外部 Agent 提供。
对我的价值
可借鉴或复用任务入口、权限、数据模型和进度展示，减少管理层建设；自主规划、任务领取、工具执行、失败恢复和验收仍需补充。

关键判断
它是带业务后台的任务管理平台。MCP 提供外部 AI 的操作接口；是否执行任务、如何执行以及如何确认完成，由成员或外部执行系统决定。

从讨论到结论

01

完整的管理产品

前端呈现任务，后端保存数据、控制权限并处理业务事件。

02

人工协作可独立运行

成员执行工作，再更新负责人、状态与完成标记。

03

自动执行需要外部接入

MCP 提供操作入口，Agent 与执行调度需要另外实现。

01 / 引导图与底层架构

能力、架构、接入与扩展

下载 PNG下载 SVG

同一份任务，多种视图

parentId 表示子任务；statusId 对应看板状态；complete 保存完成标记。依赖关系存为边，由 Vue Flow 与 Dagre 绘制和布局。

每次操作都经过后端

Vue 界面或 API 客户端发出请求，经 Express 路由、鉴权与权限检查进入业务层，再通过 Drizzle ORM 写入 PostgreSQL。

事件触发管理动作

任务变化触发 EventBus；pg-boss 处理异步或定时业务。Centrifugo 可提供实时推送，完成周期任务可生成下一实例。

02 / 原生能力

它已经能管理哪些工作？

以下是主分支与官方文档描述的能力。
本次未部署验证每项功能。

01

项目与任务

项目、列表、任务、嵌套子任务；负责人、优先级、标签、日期、搜索和历史记录。

适合：需求拆分、缺陷记录、交付清单。

02

视图与工作流

列表与自定义看板、状态、任务依赖图、Sprint 和重复任务。

适合：迭代安排、进度跟踪、依赖梳理。

03

协作与权限

组织、项目成员、角色与细粒度权限；API Token 的操作与项目范围；SSO 相关能力。

适合：团队分工、访问控制、服务账号接入。

04

工时与统计

时间记录、计费与非计费工时、工作量统计，以及项目收入和支出相关报表。

适合：内部交付管理、工时与项目成本记录。

05

开发与消息集成

GitHub、GitLab、Gitea 的 Issue 同步；Slack 与 Telegram 的通知和任务交互。

Issue 变化同步到任务；完成状态可回写。

06

开放接口与多端

HTTP API、TypeScript 客户端、MCP、签名 Webhook；Web 与 Capacitor 移动端。

适合：脚本、外部 AI 和业务系统接入。

依据：Gimanh/taskview-community · README · Gimanh/taskview-community · 仓库集成 · Gimanh/taskview-community · 消息集成

03 / 使用场景

把平台放在具体工作中理解

不同场景共用任务管理能力，
实际工作的执行者不同。

内部研发与迭代

输入
需求、缺陷、Issue、成员与迭代安排。

过程
拆成任务和子任务，设置依赖、负责人、状态、日期和工时。

输出
项目进度、任务历史、工时统计与消息通知；代码由开发人员编写。

个人与内部交付管理

输入
个人计划或客户工作的内部记录。

过程
整理工作清单，记录时间、金额和完成情况。

输出
可追踪的交付记录与统计。向客户开放实例需另核实商业许可。

人和 Agent 共用任务面板

输入
人提出任务，Agent 经 MCP 或 API 获取任务上下文。

过程
由外部 Agent 使用自己的工具执行；调度和验收策略另外实现。

输出
状态、备注、产物链接和执行记录回写；形成可视化跟踪。

04 / 入口与出口

入口接收操作，出口提供状态与事件

区分任务记录、管理自动化和实际执行产物，
便于设计后续系统接口。

入口 / 现有接口

什么可以进入 TaskView？

人工操作
Web 或移动端创建项目、任务和成员，更新状态、日期、备注与工时。
程序请求
脚本或服务通过 HTTP API / TypeScript 客户端读取与修改任务，后端统一校验身份和权限。
AI 工具调用
本地 stdio MCP 或共享 HTTP MCP 将结构化工具调用转为 API 请求；授权范围与用户权限共同限制操作。
外部平台事件
GitHub / GitLab / Gitea 的 Issue 事件触发同步；已配置并绑定身份的 Slack / Telegram 可触发任务操作。
出口 / 现有管理结果

TaskView 可以输出什么？

任务数据与视图
HTTP / MCP 返回可访问的项目与任务上下文；界面展示列表、看板、关系图、状态、历史及统计。
通知与业务事件
持久化通知、邮件或消息平台通知；可选 Centrifugo 实时推送；签名 Webhook 将事件交给外部系统。
关联 Issue 状态
TaskView 中完成或重开已映射任务，可回写对应 Issue 的关闭或打开状态。
外部执行产物回流
成员或 Agent 产生代码、文件、测试报告等，再通过任务备注、外部链接和状态回写供管理层展示。完整产物归档与验收是建议扩展。

管理自动化和执行自动化要分别设计
平台能依据任务事件通知其他系统、生成周期任务。自动编写代码、操作浏览器、运行测试和验收交付，需要外部 Agent 的工具与执行机制。

依据：Gimanh/taskview-community · TypeScript API 客户端 · Gimanh/taskview-community · MCP

05 / 本地与后台 Agent 接入

谁来执行任务？

切换场景，查看职责、接入路径与所需补充。

原生使用方式

成员执行，平台协调。

以“开发一个网站”为例：平台承载任务和进度，成员在设计、开发和测试工具中完成实际工作。

  1. 1
    建立项目并拆分任务

    首页设计、登录开发、支付测试。

  2. 2
    分配负责人和时间

    设置优先级、依赖关系与迭代。

  3. 3
    成员执行并更新状态

    进行中 → 待评审 → 标记完成。

  4. 4
    后台保存与通知

    数据库记录变更，事件模块处理后续动作。

平台的工作

把协作过程记录清楚

谁做什么
负责人、项目角色与访问权限。
做到哪里
状态、子任务、历史和工时。
何时完成
日期、依赖与成员确认的完成标记。

普通项目管理可独立运行，无需 Agent。

现有 MCP 接入

本地 Agent 通过 stdio 操作任务。

兼容 MCP 的本地 AI 客户端启动 taskview-mcp，再转发请求到云端或自托管的 TaskView API。stdio 服务需要 Node.js 24 或以上。

  1. 1
    准备 TaskView API 地址与 Token

    Token 的项目和操作范围与用户权限共同限制访问。

  2. 2
    本地启动 MCP 服务

    npx -y taskview-mcp，配置 URL 与 Token。

  3. 3
    Agent 读取、执行与回写

    Agent 自己提供文件、终端等执行工具；MCP 负责任务操作。

通用 MCP 配置示例

{
  "mcpServers": {
    "taskview": {
      "command": "npx",
      "args": ["-y", "taskview-mcp"],
      "env": {
        "TASKVIEW_URL": "https://api.example.com",
        "TASKVIEW_TOKEN": "tvk_your_token"
      }
    }
  }
}

替换为自己的服务地址和 Token。凭据保存在客户端或服务配置中。

现有接口 + 建议执行桥接

后台 Agent 可持续接入，调度需补充。

已有共享 HTTP MCP 和直接 HTTP API 两条入口。若希望任务创建后自动执行，可增加 Webhook 接收器与外部 Worker。

  1. 1
    选用共享 HTTP MCP 或 API

    MCP 的 /mcp 接收调用者 Bearer Token；兼容客户端也可走 OAuth。

  2. 2
    外部服务发现待执行工作

    可轮询任务，或接收 TaskView 的签名 Webhook。

  3. 3
    由我们控制任务领取与执行

    实现去重、并发、超时、失败恢复及工具环境。

  4. 4
    验收后回写结果

    保存产物链接、日志与状态，按需要由人确认。

接入契约

服务入口
https://mcp.example.com/mcp
或自己的 TaskView HTTP API。
身份与范围
每个调用者使用自己的 Token；操作范围受用户权限限制。
云客户端 OAuth
若客户端依赖动态注册，需在 API 配置 OAUTH_DYNAMIC_REGISTRATION=true；默认关闭。
事件触发
Webhook 触发接收器。TaskView 的事件投递重试与 Agent 执行重试分别处理。
能力边界
接口可用不等于已有任务自动领取与执行调度。

当前场景：成员执行实际工作，TaskView 记录与协调任务。

依据：Gimanh/taskview-community · MCP 接入与 OAuth · Gimanh/taskview-community · Webhook 事件投递

06 / 建议扩展

要形成自动执行闭环，还需要什么？

下表的扩展项是我们的设计方向，
尚未在本次研究中实现。

扩展方向TaskView 可提供的基础需要我们实现的部分
任务领取与调度任务、状态、负责人、API 与事件。执行记录、原子领取或外部租约、并发限制、事件去重。
执行环境与工具任务描述与上下文读取。本地或服务器 Runner、隔离工作区、工具权限、资源与时间限制。
执行失败与恢复历史、状态更新、Webhook 投递记录。Agent 的超时、重试、断点恢复和人工接管。
结果与验收任务备注、状态与外部链接承载能力。代码或文件产物归档、测试与验收规则、审核后确认完成。
多 Agent 协作子任务、依赖图、项目角色。Agent 能力路由、交接、依赖约束执行和结果汇总。

两个边界需要保留：依赖图表达任务关系；执行顺序约束需由调度层实现。Git 集成目前主要围绕 Issue，同步范围应按源码确认，不能预设 PR、提交和 CI 状态已全面关联。

07 / 对我的价值

复用管理层，把精力投入执行层

这是结合我们关注的 Agent 系统作出的判断，
以实际接入测试决定是否采用。

可参考

少从零搭一套任务管理

界面、任务模型、权限、API 与事件接口可为执行系统提供管理入口。适合研究任务如何结构化、如何受控地交给外部程序。

研究价值有限的方向

自主执行机制要看其他实现

当前未看到内置的自主规划、Agent 自动领取任务、工具执行与结果验收闭环。研究这些机制时，本项目可作为外围管理层参考。

研究层面的价值

观察任务模型、角色权限、MCP 授权与事件处理如何组合。适合学习一个完整管理产品怎样向人和外部程序提供一致入口。

工程层面的价值

若与现有技术栈、部署条件和许可范围匹配，可减少管理界面和基础业务的重复建设；仍需验证版本兼容、权限、并发与升级维护。

当前取舍

保留为 Agent 管理层候选和接口参考。先验证一个 Agent 读取并完成一条测试任务，再决定是否投入后台桥接和多 Agent 调度。

建议的接入顺序 / 尚未实施

  1. 01只读接入

    连接测试项目，验证读取与权限范围。

  2. 02受控回写

    让一个本地 Agent 修改测试任务并记录结果。

  3. 03后台触发

    补充 Webhook 接收器、去重与任务领取机制。

  4. 04执行与验收

    增加工具环境、产物、测试和人工确认。

许可影响使用范围

当前是 Source-Available 许可。个人、家庭与组织内部使用及自托管被允许；组织的员工及代表组织工作的承包商属于许可用户。向外部客户或第三方开放实例，即使免费，也需要另行商业许可。托管 SaaS 和竞争产品同样受限制。
